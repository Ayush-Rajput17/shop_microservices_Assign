# Extraction Plan: Notifications Module

## Why Notifications First

I would extract the notifications module first. It has the smallest and clearest responsibility: writing confirmation messages to the outbox. Its public API is already narrow (`send` and `sent`), and it receives order information through the `order.placed` event rather than through a direct dependency from orders. That makes it the lowest-risk module to move behind a process or network boundary. Inventory and payments own synchronous decisions in the order flow, while notifications is already naturally asynchronous and can tolerate eventual delivery.

## Step 1: Define the Extraction Boundary

I would make `notifications/index.ts` the only application-facing contract. The extracted service would own:

- Message creation and message IDs.
- The outbox persistence currently used by `notifications/repo.ts`.
- Handling the `order.placed` event and creating the confirmation message.

The order module would publish the event and would not import notification implementation files or call `send` directly. `sent` would remain a test/admin-facing read API during the transition, but production code would not depend on it.

## Step 2: Identify Dependencies and Contracts

I would document the event and API contracts before moving code:

- Input event: `order.placed` with `orderId`, `email`, and `amountPaise`.
- Delivery behavior: one confirmation message for each successfully published order event.
- Read behavior during migration: `sent()` returns the messages visible in the local outbox.
- Failure behavior: a notification failure must not make the order placement fail; the event bus isolates handler errors.
- Current dependencies: the event bus and the outbox store.

I would also add contract tests for the subscriber and message shape so the in-process implementation and the extracted implementation must satisfy the same behavior.

## Step 3: Extract Behind an Adapter

I would create a notifications service process or package with the same event handler and a small adapter at the current application boundary. The adapter would translate the local `order.placed` event into the extracted service's command or message format and translate any required response back into the existing API.

Initially, the adapter would keep the existing in-memory implementation as the fallback. The event schema would be versioned before adding a transport, and message IDs would be generated by the notifications service so ownership does not move accidentally back into orders.

## Step 4: Migrate Callers Incrementally

I would first register the extracted subscriber alongside the current subscriber in a non-production verification mode, ensuring that duplicate delivery is prevented with an idempotency key such as `orderId` plus event version. After comparing outputs, I would switch the event-bus subscription to the adapter and remove the in-process subscriber.

Orders would remain unchanged apart from publishing the stable event contract. Any code reading `sent()` would use a notifications-owned query endpoint or test double rather than reaching into the repository. The migration would be released behind a feature flag so traffic can be moved gradually.

## Step 5: Validate, Observe, and Remove the Old Path

Before and during rollout I would run the boundary, event-bus, flow, and notifications contract tests. I would also verify that each successful order produces exactly one confirmation, failed orders produce none, duplicate events are idempotent, and notification failures do not block later event handlers.

In production I would monitor publish counts, delivery success/failure, latency, retries, duplicate suppression, and outbox growth. I would keep the old in-process path available for rollback until these metrics are stable. After the rollback window, I would delete the old notifications implementation and adapter fallback, then rerun the full test suite and boundary checker.
